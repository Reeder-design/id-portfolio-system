# Portfolio Asset & Evidence Map

## Purpose

This map defines the public-safe evidence the portfolio should show for each major project or capability area.

The goal is not to add screenshots for the sake of having visuals. Every asset should prove a specific claim already made in the portfolio: a design decision, a workflow, an interaction pattern, an operational judgment, or a finished deliverable.

## Evidence Principles

1. **Prove the decision, not just the software.** A recreated curriculum map is stronger evidence than a generic Rise screenshot when the claim is curriculum architecture.
2. **Build public-safe evidence from scratch.** Use fictional data, neutral labels, synthetic records, and generalized workflows. Do not reproduce confidential source material.
3. **Prefer working artifacts over flat mockups.** If the real skill is interaction design, workflow logic, scenario design, or automation, let the visitor interact with a safe reconstruction.
4. **Do not rebuild proof that already exists.** The AI Evaluation, MEDDPICC, and Pursuit demos are already live evidence. They need integration/polish, not replacement.
5. **Keep evidence proportional.** One strong artifact can prove more than five decorative thumbnails.
6. **Reuse visual and interaction patterns.** Evidence across learning design, systems, and data should feel like one portfolio system rather than unrelated mini-sites.
7. **Keep unsupported outcomes out.** Assets can demonstrate process, reasoning, structure, and delivered work without inventing learner counts, ROI, revenue impact, satisfaction scores, or performance lift.

## Status Legend

- **BUILD** — create a new public-safe artifact.
- **EXISTING** — strong interactive evidence already exists; only integrate or polish it.
- **CAPTURE** — create a lightweight preview image/animation from an existing public artifact when useful for discovery.
- **LATER** — useful but not necessary for the first evidence release, or depends on approved real media.

# Master Evidence Map

## 1. Enterprise Sales Certification Pathway

**Portfolio claim to prove:** I can turn broad, changing source material into a maintainable learning architecture with role-based routing, assessment alignment, QA, LMS delivery, and reporting support.

### Primary evidence

**A. Curriculum Architecture Map — BUILD**

Public-safe interactive/recreated map showing:
- Core Path
- Regional Extension
- Optional Foundations
- Practice
- Assessment
- Remediation / handoff

The visitor should be able to switch learner profiles or route types and see which parts of the pathway are required, regional, or optional.

**Why it matters:** proves curriculum architecture and audience/routing decisions rather than merely showing course screens.

**Placement:** Enterprise Sales Certification case study, near Learning Architecture / Audience Strategy.

**B. Objective + Assessment Blueprint — BUILD**

A compact interactive table or blueprint connecting:

`Objective → Seller task → Practice → Assessment evidence → Remediation`

Use fictionalized/sanitized examples already represented in the project record.

**Why it matters:** proves backward design, assessment strategy, and alignment.

**Placement:** Enterprise Sales Certification case study, near Objective Alignment / Assessment Strategy.

### Optional later evidence

**C. Certification QA / Release Board — LATER**

A public-safe release flow showing design QA, accessibility/interaction QA, SME review, assessment review, LMS test, launch, and post-launch triage.

The existing case-study detail flow already communicates much of this, so this should only become a separate artifact if it adds meaningful interactivity.

# Shared Evidence System

The individual artifacts should feel related even when their interactions differ.

## Reuse where practical

- existing portfolio palette, typography, icon sprite, buttons, cards, focus states, and reduced-motion conventions
- existing project/case-study page layout rather than a new evidence-page design for every artifact
- the same fictional-data standards across system and automation examples
- the same evidence labels: **What this proves**, **Try it**, **How it works**, **Public-safe reconstruction**

## Artifact locations

Prefer colocating a project-specific interactive artifact under its public project directory when it belongs to one case study.

Use shared public assets only for genuinely reusable media or data files.

Synthetic source/output files should live in clearly named public evidence folders and never resemble real internal filenames, account IDs, learner identifiers, or customer records.

## Structured project assets

When a generated/structured case study receives a public file that should appear in its Evidence section, add it through the existing project `assets` model with `publish: true` rather than creating a second evidence registry.

Bespoke interactive demos that are themselves the project can remain linked as live experiences rather than being duplicated into `assets`.

---

# Privacy Checklist for Every Evidence Build

Before an artifact becomes public:

- all people, companies, customers, learners, accounts, IDs, emails, and records are fictional unless already intentionally public
- no internal screenshots or copied UI configuration
- no unreleased product names or messaging
- no reviewer names/comments/internal links
- no real learner or customer metrics
- no credentials, tokens, environment details, or private file paths
- no source content copied merely because the final wording was sanitized
- public copy clearly labels reconstructions where needed

---

# Definition of Done for Phase 24

Phase 24 is complete when:

1. every major portfolio project/capability has a documented evidence decision;
2. each planned artifact has a clear claim, format, privacy boundary, and placement;
3. existing interactive proof is reused instead of redundantly rebuilt;
4. Wave 1 build order is agreed and ready for implementation;
5. no evidence plan depends on confidential source material being uploaded to the public repository.
