The mental model

Portfolio Manager operates on your local clone of id-portfolio-system. A local file change is not the same thing as a Git commit, and a Git commit is not the same thing as a public deployment.

The system has four layers:

  • Structured source: portfolio-data/projects/*.json contains project information the dashboard can understand.
  • Public website: portfolio/ contains the HTML/CSS/JS/assets GitHub Pages publishes.
  • Maintenance documentation: docs/ and portfolio-data/version.json describe the portfolio system and releases.
  • Git/GitHub: branch → commit → push → pull request → review → merge → deployment.

Key rule: Portfolio Manager currently does not commit, push, merge, or publish automatically.

Starting and signing in

From the repo root in VS Code:

source .venv/bin/activate

On first secure setup, run python portfolio-manager/setup.py. This asks for your password locally, writes a password hash and random Flask secret to the Git-ignored .env file, and creates the private .portfolio-manager/ workspace.

Start the app with python portfolio-manager/app.py, then open http://127.0.0.1:5055. Port 5055 avoids the common macOS AirPlay Receiver conflict on port 5000. The app explicitly binds only to localhost and normal debug mode is disabled.

Privacy and security

The dashboard code can live in a public repository without giving strangers control of your portfolio. The operating credentials and private runtime data do not live in Git.

  • .env contains the local secret and password hash and is ignored by Git.
  • .portfolio-manager/ stores requests, uploads, temporary files, and backups and is ignored by Git.
  • Every dashboard route except the login/static assets requires an authenticated session.
  • Every POST action requires a CSRF token, preventing another webpage from silently submitting a modifying request to your local app.
  • Sessions expire after eight hours.

You should still review uploads before intentionally moving anything from the private workspace into the public repository.

Run Full Validation

This is a read-only health check. It runs the same portfolio validation set used by the GitHub pull-request workflow: site links/assets, structured content, renderer compatibility, project-generator behavior, versioning, generated-document freshness, and Portfolio Manager security rules.

Changes: nothing.

Use it: after meaningful edits and before committing/pushing a branch.

Refresh Docs

This action runs scripts/update-docs.py. It reads your structured projects and version data, then rebuilds the maintenance documentation describing the portfolio.

Typical affected files are docs/content-inventory.md, docs/portfolio-map.md, and docs/changelog.md.

It does not refresh the public website. It does not rewrite your homepage, regenerate project HTML, commit, push, merge, or deploy.

Memory shortcut: Refresh Docs = refresh the paperwork about the portfolio.

Version releases

A version bump records an intentional release in portfolio-data/version.json, refreshes release documentation, and creates a historical snapshot under docs/versions/.

  • Patch: small corrections/refinements, e.g. 1.0.0 → 1.0.1.
  • Minor: meaningful new project/feature, e.g. 1.0.0 → 1.1.0.
  • Major: major architecture/redesign, e.g. 1.0.0 → 2.0.0.

Do this once near the end of a meaningful release, not for every experimental edit. A version bump still does not commit or publish anything.

Requests and private uploads

Request a Change and New Content Request save work orders. They do not perform arbitrary site edits yet.

Requests and attached source/reference files are stored in .portfolio-manager/, not portfolio-data/, so a normal git add . will not pick them up.

Use requests when you have an idea, source material, or future edit you want the system to remember without changing the actual portfolio yet.

Public Asset Library

The Asset Library is deliberately different from private request uploads. It manages files that you have decided are safe to become part of the public portfolio.

Uploaded assets are copied under portfolio/assets/project-assets/<project-id>/ and registered in that project's structured assets array. The file and JSON association are both local changes until you commit/push/merge them.

Important: because the file lives under portfolio/, it may become publicly reachable after a future merge even when no page visibly links to it. Never put confidential, proprietary, customer-identifying, or unreleased material in the Asset Library.

  • Add Public Asset: copies an allowed file into the managed public folder and records its type/path/alt/caption. Images require alt text.
  • Save Metadata: updates alt text or caption in project JSON and refreshes documentation.
  • Replace File: replaces the bytes at the same public path. The extension must stay the same so custom-page references are not broken. Site validation runs and restores the old file if validation fails.
  • Remove Asset: removes the JSON association and local public file, then validates. If another page still depends on the file, Portfolio Manager rolls the removal back.

HTML, JavaScript, CSS, SVG, executables, and archive uploads are intentionally blocked from this interface. Custom code remains a deliberate developer workflow rather than a file-upload shortcut.

Creating a standard project

New Standard Project is different from a request: it creates real portfolio files using the project generator.

The flow is: form → slug/taxonomy path → structured JSON → standard page when public-safe → validation → documentation refresh.

Use Building while developing. Use Needs Sanitization when the structured record may exist locally but should not be rendered as public-ready content.

Creating a project does not commit, push, merge, or publish.

Editing structured project data

Save Project Data edits the corresponding portfolio-data/projects/*.json record. It then validates the structured content and refreshes documentation. If validation fails, the JSON edit is rolled back.

Fields such as title, audience, role, objectives, outcomes, skills, tools, status, confidentiality, and asset associations live in this structured source.

Saving JSON does not necessarily update public HTML. What happens next depends on whether the page is standard or custom.

Standard pages vs. custom pages

Standard Page

A standard page was generated from structured project data and templates/project-page/index.html. It carries a marker telling Portfolio Manager it is safe to rebuild.

Workflow: edit structured data → Save Project Data → Regenerate Page → preview → Run Full Validation.

Custom Page

A custom page contains bespoke HTML/CSS/JavaScript such as scoring, simulation logic, dashboards, or other interaction behavior. Portfolio Manager may update its metadata JSON but deliberately prevents the generic renderer from overwriting the custom experience.

Regenerate Page

For a Standard Page only, this reads the latest project JSON and shared project template, then replaces that project's generated public index.html. Site validation runs afterward.

This changes public HTML locally. It still does not commit, push, merge, or publish.

Git and publishing

VS Code may show M for a modified tracked file or U for a new untracked file. Neither means the file is committed or public.

Your publishing path remains: review local changes → git status → commit on a branch → push → pull request → review → merge → GitHub Pages deployment.

The live site deploys from portfolio/. Changes only to JSON/docs/dashboard infrastructure do not visibly alter the public site unless the relevant public HTML/CSS/JS/assets also change.

When something goes wrong

Keep the terminal running while using Portfolio Manager. If the browser errors, the terminal normally contains the useful Python message.

If files changed unexpectedly, run git status before deleting or resetting anything. Uncommitted local changes are usually recoverable.

To stop the app, use Control + C. Closing the terminal only stops Flask; it does not delete your files.
