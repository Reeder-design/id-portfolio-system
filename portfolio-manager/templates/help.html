Memory shortcut: if it already exists, Manage. If it is new, Create. If the source is private, Prepare it in Reference Library first.

The button dictionary: “what happens if I click this?”

This is the safest mental model for Portfolio Manager. Most buttons do less than “publish.”

Save Edits / Save Project
Writes reviewed changes to your local working copy. Not live.
Approve & Apply Locally
Applies one reviewed page-AI proposal locally, validates it, then gives you Keep/Revert. Not live.
Keep
Accepts a validated local result so you can continue working with it. Still not live.
Approved for Portfolio Use
Allows a sanitized derivative to be used as source context. It does not publish that source.
Full Validation
Checks health/safety. It changes nothing.
Commit
Creates a Git history checkpoint on your Mac. Still not live.
Publish to GitHub
Pushes approved committed changes to GitHub. This is the step that can make site changes live.
Merge PR
Merges a feature branch into the codebase. This is for developing Portfolio Manager, not normal portfolio-content publishing.

If your question is “did I just make this public?” Usually no. A portfolio change becomes publishable only after it is committed and explicitly pushed with Publish to GitHub.

Two Git workflows that should not be confused

1. Using Portfolio Manager

This is normal portfolio work: edit/create locally → preview → validate → commit → Publish to GitHub. You do not need a feature PR for every content change.

2. Developing Portfolio Manager itself

When we are adding a new Portfolio Manager feature, the workflow is different:

  1. I make the change on a GitHub feature branch and open a PR.
  2. You pull that feature branch into VS Code and restart Portfolio Manager.
  3. You perform focused UAT: test only the new behavior and tell me what worked or felt wrong.
  4. I refine the same PR until you approve it.
  5. You explicitly say merge PR#.
  6. After merge, switch back to main and pull the merged code.

Branch: temporary version of the code for testing. PR: proposed code change waiting to be merged. UAT: your real-user test. Merge: accepts that tested feature into main.

Memory shortcut: branch/PR = we are developing the tool. Save & Publish = you are using the tool to publish portfolio content.

Where information lives: private vs. public

.env
Local secrets: password hash, Flask secret, optional AI API key. Git-ignored.
.portfolio-manager/
Private working data: notes, AI proposals/reviews, backups, Content Briefs, Reference Library files, Hiring Guide editorial libraries, temporary uploads. Git-ignored.
portfolio-data/
Git-tracked structured content. Treat it as publishable repository content.
portfolio/
Public-candidate website files and managed assets. Anything here may become reachable after publishing.

Rule: confidential/proprietary/unsanitized source material belongs in Reference Library, not portfolio/ or portfolio-data/.

Important: “private” here means kept in your local Git-ignored Portfolio Manager workspace. It does not mean Portfolio Manager can automatically decide whether professional material is legally/contractually safe to disclose—you still make that judgment.

Manage existing portfolio work

Use Manage Content when the page/project already exists. The hierarchy mirrors the public portfolio so you can think in pages rather than repository architecture.

  • Visible content: edit recognizable headings, paragraphs, labels, lists, buttons, and supported interaction text.
  • Private notes: use for reminders/ideas you do not want public.
  • Project identity: titles and structured project data stay connected so references/docs can remain consistent.
  • Related References: review outgoing project connections, incoming references, and deterministic relationship suggestions. Suggestions are never added automatically.
  • Component Registry: check which reusable interaction/presentation patterns already exist and where they are implemented before creating another version.
  • Project Assets: upload/preview/replace/remove public-candidate assets beside the relevant project editor.
  • Structural/visual/code change: use page-aware AI rather than forcing the change through a plain-text field.

Related References has two jobs. The project workspace manages structured project-to-project relationships; the rename workflow checks existing visible labels/cards after a title change. Both are deterministic—not AI—and both require your approval before relationship/reference changes are written.

Component Registry is documentation-first. Recording a component on a project documents design-system usage. It does not inject markup into a bespoke page. Components marked template-supported are already owned by the standard generated-project renderer.

Images and project assets

Routine project assets live inside the relevant project/custom-page editor. Use the full Asset Library only when you want the broader asset-management view.

  • Uploading an asset associates it with a project; it does not automatically place it into the public page layout.
  • Images require alt text.
  • Upload/replacement requires a public-safe confirmation.
  • Removal checks whether public HTML/CSS/JavaScript still references the file.
  • If the file is private source material rather than a public portfolio asset, use Reference Library instead.

Which AI tool should I use?

The easiest way to avoid AI confusion is to choose the tool based on the job.

Page-aware AI
I want to change one existing page, especially layout/interaction/code.
AI Portfolio Review
I want feedback on the public portfolio as a whole.
Ask AI About This Resource
I want to understand what one private source demonstrates or could support.
Sanitization Review
I want help finding details that may need to be removed/generalized before portfolio use.
Create Content Lab
I want to build a new portfolio project from an idea/evidence/source.
Advanced AI Drafting Helper
I need a one-off rewrite, analysis, summary, placement suggestion, or draft.

AI rule: AI can propose, analyze, flag, or draft. You decide what gets applied, sanitized, approved, saved, or published.

Page-aware AI edits

Use this from an existing page editor for changes such as spacing, cards, interactions, visual hierarchy, or code-heavy behavior.

What AI sees: the selected public page, relevant public design-system CSS, and your request. Private page notes, Reference Library files, credentials, Git history, and unrelated files are excluded.

Workflow: Request → private proposal → review exact anchored edits → Approve & Apply Locally → validation → real local preview → Keep or Revert.

Applying locally is not publishing. A private backup is created before the approved operations are applied.

Reference Library: when the source is private or not ready

Use the Content Workspace & Reference Library when professional source material may be useful later but should not simply be dropped into the public repo.

The original is preserved unchanged. Sanitized work is stored separately. Typical statuses are Private Source, Needs Review, Sanitization In Progress, Sanitized Draft, and Approved for Portfolio Use.

Approved for Portfolio Use does not publish a file. It means the sanitized derivative is eligible to be attached to a Content Brief as trusted source context.

Ask AI About This Resource

Use this to identify skills demonstrated, evidence present, evidence gaps, reusable elements, possible portfolio projects, and likely placement.

For text-extractable files, you review the exact extracted text before send. For supported images, you review the actual image; image pixels are not locally OCR/preflighted, so a separate visual acknowledgement is required. Private notes, tags, approval notes, unrelated Reference Library resources, and credentials are not sent.

Sanitization Review

AI flags; you decide. For each finding you can Keep, Remove, Generalize, Rewrite, Replace, Crop/redact, or mark it intentionally public-safe. The original source is never overwritten.

Create Content Lab: build the idea before the page

  1. Content Brief: define what you are making, why, audience, story, evidence, interaction, visual direction, safety constraints, and personal direction.
  2. Approved Sources: optionally attach approved sanitized derivatives. Private originals stay outside the brief/build AI context.
  3. AI Content Plan: review proposed format, placement, sections, interactions, assets, evidence gaps, safety notes, tasks, and writing direction.
  4. Approve Plan for Build: explicit human gate before build generation.
  5. Build Proposal: AI proposes the structured public case-study fields; no public files are written yet.
  6. Human review: edit the exact proposed public content.
  7. Create Local Project & Validate: write local files through the controlled renderer/generator and validate them.
  8. Preview → Keep or Revert: inspect the real local result before accepting it.
  9. Continue toward publishing: kept builds move into Related References and the normal publishing flow.

If the Content Brief or approved source context changes, an older AI plan may become stale. Regenerate it rather than assuming the old plan still matches the evidence.

Advanced AI Drafting Helper

Use this for isolated work rather than a full project workflow. You can paste text or attach supported files.

File workflow: Prepare Locally → review exact text/images → acknowledge provider/authorization/sensitivity/visual boundaries → Generate Proposal.

For images, you see the actual preview but image pixels are not locally OCR/preflighted. Temporary binary uploads are Git-ignored and removed after successful generation or when you discard the request.

After generation:

  • Use in Existing Content: stage the draft in a real editor. Nothing saves until you save the editor.
  • Create Something New: prefill an unsaved Content Brief.
  • Save for Later: update private proposal status only.

Hiring Guide Library: maintain the answers behind Ask Haley

Use this private workspace when you want to add, revise, audit, or organize canonical hiring-manager answers. Import the canonical JSON library once; optionally import the Markdown editorial copy beside it.

  • Browse/search/filter: find Q&A by text, category, confidence, or evidence status.
  • Edit Q&A: maintain the canonical answer, evidence IDs, tags, source basis, confidence, question variants, follow-ups, and implementation notes.
  • Edit evidence: maintain what each evidence record supports and whether it is demonstrated, emerging, inferred, or audited.
  • Backups: each edit creates a private previous-version copy under .portfolio-manager/hiring-guide/backups/.
  • Export: download the current private JSON or preserved Markdown source.

Preview Public Sync

When the private answers are ready, use Preview Public Sync. It creates a private proposal first and shows which private Q&As matched existing public questions, which would be added, which fields would change, and any evidence/editorial warnings.

Use the Routing simulator to ask a hiring-manager question against the proposed public library before writing anything. The simulator mirrors the live deterministic scoring logic.

Apply Public Sync Locally + Validate requires an exact confirmation phrase. It creates a private recovery backup, refuses stale/destructive proposals, writes only the two local public FAQ data files, and runs Full Validation. If validation fails, the old files are restored automatically.

Important: Public sync apply is still not publishing. It creates local public-candidate changes that you should preview in the real Ask Haley page before using the normal Save & Publish workflow.

Publishing: the part that actually makes changes live

Local edits are not live. Validation is not live. Keep is not live. A local Git commit is not live.

  1. Finish the relevant Manage/Create/Related References work.
  2. Preview the real local page.
  3. Run Full Validation.
  4. Open Save & Publish.
  5. Review changed files and select exactly what belongs in the commit.
  6. Inspect the diff: does Git show only what you intended?
  7. Use Validate & Commit Changes. This creates a local checkpoint.
  8. Use Publish to GitHub when you want the committed result sent to GitHub.

GitHub Pages can deploy the site after the push. Portfolio Manager blocks known private paths, force-push, silent merge/rebase behavior, publishing with uncommitted changes, and publishing when GitHub has newer commits.

Git/GitHub without developer-brain

Repository / repo
The whole project folder plus its version history.
Working copy
The files currently on your Mac.
main
The primary accepted version of the project.
Feature branch
A temporary alternate version used to develop/test a change safely.
Commit
A named checkpoint in Git history.
Push
Send local commits to GitHub.
Pull
Bring newer GitHub commits down to your Mac.
PR / Pull Request
A request to merge a feature branch into another branch, usually main.
Diff
The exact line/file changes between versions.
Merge
Combine an approved branch/PR into the target branch.

You do not need to memorize Git commands to use Portfolio Manager. The point of these definitions is to help you interpret warnings and know whether you are in a content-publishing workflow or a tool-development workflow.

AI privacy: “what exactly leaves my Mac?”

There is no single universal AI context. Each AI workflow has its own disclosure boundary.

  • Page-aware AI: selected public page + relevant public CSS + your request.
  • Portfolio Review: public portfolio only.
  • Reference Resource Analysis: the exact extracted source text or reviewed supported image, after acknowledgement.
  • Sanitization: the specific source text under review, after disclosure/authorization checks.
  • Create Content: saved Content Brief, current plan/context, taxonomy, and approved sanitized source text—not the private originals.
  • Advanced AI Helper: only the pasted/prepared reviewed request content and attachments you approve.

The API key itself stays in local .env. If a workflow shows a sensitivity/credential warning, stop and understand it before proceeding.

Things you usually do not need during normal content work

Refresh Documentation, Version Release, and other Advanced Maintenance controls exist for system upkeep, not routine page editing.

Still intentionally deferred: curated Theme Editor, automated visual sanitization/redaction, additional Portfolio Review lenses/web research, and the final simplification of publishing into a more human-facing Preview → Approve → Publish surface.

When something goes wrong: diagnose before fixing

  • Portfolio Manager is not running: from the repo root run python portfolio-manager/app.py.
  • Preview is blank: from portfolio/ run python3 -m http.server 8000.
  • Session expired: sign in again. The timeout does not delete your files.
  • AI says setup is needed: open AI Settings and test the configured key/model.
  • AI request is blocked: read the sensitivity/credential warning; do not bypass it just to make the workflow continue.
  • Reference source cannot be approved: a separate sanitized derivative must exist first.
  • Content plan is stale: regenerate it after changing the brief or approved source context.
  • Asset removal is blocked: the file is still referenced by public code.
  • Validation fails: stop before publishing and read the first concrete failure. Do not randomly delete/reset files to make the warning disappear.
  • Publish is blocked: look for uncommitted local changes or newer GitHub changes.
  • You are testing a PR and something looks old/weird: confirm you pulled the current feature branch before assuming the remote code is wrong.

Management rule: warnings are information, not clutter. First identify which state is inconsistent—local files, private workflow state, Git history, or GitHub—then fix that state deliberately.
