Portfolio Manager

User Guide

A zero-context guide to what each control changes, what stays local, and how work moves safely to the live portfolio.

Back to Dashboard

If you forgot everything, start here

  1. Start Portfolio Manager: from the repo root run source .venv/bin/activate, then python portfolio-manager/app.py. Open http://127.0.0.1:5055.
  2. Choose the right editor: Project Content for structured projects, General Page Content for routine managed-page copy, Asset Library for approved public files, or Requests for private source material/future work.
  3. Make and preview the change: edits remain local until Git is used. Preview public pages before preparing a commit.
  4. Run Full Validation: this is a read-only health check. Fix failures before committing.
  5. Open Git Workflow: review the diff, stage exact files, validate + commit, push the feature branch, and open a pull request.
  6. Review the PR and CI: nothing is live yet.
  7. Merge only with explicit approval: GitHub Pages deploys approved changes from main. Portfolio Manager intentionally has no merge button.

Session timed out? Sessions expire after eight hours. Your files are not deleted. If Flask is still running, simply open the manager and sign in again. If the server stopped, restart it with python portfolio-manager/app.py.

Dashboard quick reference

  • Run Full Validation: reads the portfolio and runs health/safety checks. Changes nothing.
  • Refresh Docs: rebuilds maintenance documentation such as inventory, map, and changelog. It does not refresh public pages.
  • Open Project Content: edit structured project records. Standard pages can be regenerated; custom interactive pages are protected.
  • Open General Page Content: edit approved plain-text fields on managed public pages with validation and rollback.
  • Open Asset Library: manage files deliberately approved for the public portfolio.
  • Open Git Workflow: guarded branch → diff → stage → validation + commit → push → PR workflow. No merge control.
  • Version Release: record an intentional patch, minor, or major system release near the end of meaningful work.
  • New Content / Edit Requests: save private work orders and supporting files without changing public content.

The mental model

Portfolio Manager operates on your local clone of id-portfolio-system. A local file change is not the same as a Git commit, and a Git commit is not the same as a public deployment.

  • Structured source: portfolio-data/projects/*.json contains project information; portfolio-data/site-content.json contains approved general-page copy.
  • Public website: portfolio/ contains the HTML, CSS, JavaScript, and assets GitHub Pages publishes.
  • Maintenance documentation: docs/ and portfolio-data/version.json describe the system and releases.
  • Git/GitHub: branch → review → stage → validate + commit → push → pull request → review → merge → deployment.

Key rule: Portfolio Manager can automate guarded feature-branch Git mechanics, but it cannot merge a pull request or bypass review.

Starting and signing in

From the repo root in VS Code:

source .venv/bin/activate

python portfolio-manager/app.py

Then open http://127.0.0.1:5055. Port 5055 avoids the common macOS AirPlay Receiver conflict on port 5000. The app binds only to localhost and normal debug mode is disabled.

Initial secure setup uses python portfolio-manager/setup.py. You do not rerun setup just because a session expired.

Privacy and security

  • .env contains the local secret and password hash and is ignored by Git.
  • .portfolio-manager/ stores private requests, uploads, temporary files, and backups and is ignored by Git.
  • Authenticated sessions expire after eight hours.
  • Every modifying POST action requires a CSRF token.
  • The app runs only on 127.0.0.1.

Review public copy, uploads, Git diffs, and pull requests before approving publication.

Run Full Validation

This is a read-only health check. It runs the portfolio validation set used by the GitHub pull-request workflow: site links/assets, structured project content, structured general-page copy, renderer/template compatibility, project-generator behavior, versioning, generated-document freshness, Git workflow guardrails, and Portfolio Manager security/runtime rules.

Changes: nothing.

Use it: after meaningful edits and before commit. The Git Workflow runs the same suite automatically before creating a commit.

Refresh Docs

This runs scripts/update-docs.py and rebuilds maintenance documentation from structured project/version data.

Typical affected files are docs/content-inventory.md, docs/portfolio-map.md, and docs/changelog.md.

It does not refresh the public website. It does not rewrite the homepage, regenerate project HTML, commit, push, merge, or deploy.

Memory shortcut: Refresh Docs = refresh the paperwork about the portfolio.

Version releases

A version bump records an intentional release in portfolio-data/version.json, refreshes release documentation, and creates a historical snapshot under docs/versions/.

  • Patch: small corrections/refinements, such as 1.0.0 → 1.0.1.
  • Minor: meaningful new project/feature, such as 1.0.0 → 1.1.0.
  • Major: major architecture/redesign, such as 1.0.0 → 2.0.0.

Use a version release near the end of a meaningful release, not for every experimental edit. A version bump does not commit or publish anything.

Requests and private uploads

Request a Change and New Content Request save private work orders. They do not perform site edits.

Requests and attached source/reference files stay under .portfolio-manager/, outside normal Git tracking.

Use requests for ideas, employer/source material, drafts, or future edits you want to retain without putting them in the public portfolio.

General Page Content

This is the safe editor for routine copy on Home, About, Projects, Instructional Design, AI Training and Evaluation, Workflows, and Contact.

The source of truth is portfolio-data/site-content.json. Only approved headings and paragraphs are exposed; raw HTML is not.

  • Editable: approved headings, hero copy, introductions, and overview paragraphs.
  • Not editable here: navigation, links, buttons, tags, lists, CSS, JavaScript, layout, or custom project interactions.
  • Public-safety gate: saving requires confirmation that the copy contains no confidential, proprietary, customer-identifying, or unreleased information.
  • Fail-closed rendering: if a redesign makes an approved locator missing or ambiguous, saving fails instead of guessing.

Saving general page copy

Save Page Copy updates the structured value in portfolio-data/site-content.json and the approved text location in that page's public HTML.

General-content and public-site validation run immediately. If either fails, both the JSON and HTML change are restored.

Saving changes local files only. Preview the page, then use the separate Git Workflow when it is ready for review.

Public Asset Library

The Asset Library manages files you have intentionally approved for the public portfolio.

Files are stored under portfolio/assets/project-assets/<project-id>/ and registered in the project's structured assets array. Because this is under portfolio/, a merged file may be publicly reachable even if no page visibly links to it.

  • Add Public Asset: copies an allowed file and records type/path/alt/caption. Images require alt text.
  • Save Metadata: updates alt text or caption and refreshes documentation.
  • Replace File: replaces bytes at the same path; extension must stay the same. Validation restores the old file on failure.
  • Remove Asset: removes its structured association and public file, then validates. Referenced files are protected by rollback.

Never use the Asset Library for confidential or unsanitized source material. Use private Requests instead.

Creating and editing structured projects

New Standard Project creates real portfolio files: form → taxonomy path → structured JSON → standard public page when safe → validation → docs refresh.

Save Project Data edits the corresponding portfolio-data/projects/*.json. Validation failure rolls the JSON edit back.

Project fields include title, audience, role, objectives, outcomes, skills, tools, status, confidentiality, and asset associations.

Saving project JSON does not always change public HTML. Standard and custom pages behave differently.

Standard pages vs. custom pages

Standard Page

Generated from project JSON and templates/project-page/index.html. The current template uses the portfolio refresh styling and an interactive in-page case-study navigation.

Workflow: edit structured data → Save Project Data → Regenerate Page → preview → Run Full Validation → Git Workflow.

Custom Page

Contains bespoke HTML/CSS/JavaScript such as scoring, simulation logic, dashboards, or other interaction behavior. Portfolio Manager can update metadata JSON but deliberately prevents the generic renderer from overwriting the custom experience.

Workflow: update metadata and custom code deliberately → preview/test interaction → Run Full Validation → Git Workflow.

Regenerate Page

For a Standard Page only, this reads the latest project JSON and shared project template, then replaces that project's generated public index.html. Site validation runs afterward.

This changes public HTML locally. It does not commit, push, merge, or publish.

Git Workflow: what each step means

  1. Sync Main Safely: available only on clean main. Uses git pull --ff-only and refuses updates requiring a merge commit.
  2. Create & Switch Branch: creates a local feature/, fix/, content/, or chore/ branch from clean main.
  3. Review Changed Files: shows Git's current changed-file list.
  4. Diff Review: shows staged and unstaged line-level changes.
  5. Stage Selected Files: selects exact approved files for the commit.
  6. Run Validation & Commit: runs the full validation suite first and blocks the commit on failure.
  7. Push Branch to GitHub: pushes only the current non-main feature branch and refuses uncommitted changes.
  8. Open Pull Request: creates or opens the GitHub review path. Merge remains separate.

Git Workflow safety boundaries

  • Commits and pushes on main are blocked.
  • Force-push is not implemented.
  • Git merge and pull-request merge are not implemented.
  • .git, .env, .portfolio-manager/, .venv/, and common key/certificate files are blocked from staging.
  • Only exact paths Git currently reports as changed can be staged.
  • Full validation runs before commit.

Most important: there is deliberately no Merge button. PR approval and merge remain explicit human decisions.

Git and publishing

Your publishing path is: local edit → preview → Full Validation → diff review → stage → validation + commit on a feature branch → push → PR → CI/review → explicit merge → GitHub Pages deployment.

GitHub Pages publishes from portfolio/. A local edit, local commit, pushed branch, or open pull request is not the live website.

When something goes wrong

  • Session expired: sign in again. Your work is still on disk.
  • Browser cannot reach the manager: check whether python portfolio-manager/app.py is still running.
  • Portfolio preview says port 8000 is in use: another preview server is already running. Use the existing http://127.0.0.1:8000 or stop that server before starting another.
  • Validation fails: do not commit. Read the failure, fix the issue, and rerun validation.
  • Unexpected Git changes: inspect Git Workflow or run git status. Do not delete/reset files just to make the warning disappear.

To stop Portfolio Manager or a preview server, press Control + C in that server's terminal. Stopping a server does not delete files.
